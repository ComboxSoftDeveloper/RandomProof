# RandomProof

Замеры и проверки к статье «А чё, так можно было? Опечатка в исходниках .NET,
которой больше 20 лет» — про `System.Random`: два разных алгоритма под одним
именем и ошибка, которую не стали исправлять.

BenchmarkDotNet 0.15.8, Release, .NET 8, .NET 9 и .NET 10 в одном запуске,
со снятием машинного кода.

Статья: **[ссылка]**

## Что проверяется

| Раздел | Что смотрим | Что сравнивается |
| --- | --- | --- |
| 1 | получение числа | без начального значения, с ним, общий и криптографический |
| 2 | остальные способы | диапазон, дробное, длинное, буфер байт |
| 3 | создание генератора | два конструктора: время и память |
| отчёт `algorithms` | какая реализация досталась | пять способов создать `Random` |
| отчёт `sequence` | повторяемость | одно начальное значение против разных |
| отчёт `quality` | распределение и связь соседних чисел | три генератора |

## Результаты

### Какая реализация досталась

```
  как создан                     реализация

  new Random()                    XoshiroImpl
  new Random(42)                  Net5CompatSeedImpl
  new Random(0)                   Net5CompatSeedImpl
  new Random(int.MaxValue)        Net5CompatSeedImpl
  Random.Shared                   реализация не задана
```

`Random.Shared` реализацию не показывает: он работает иначе и создаёт
отдельный `XoshiroImpl` для каждого потока.

### Получение числа

| Способ | i9-10900KF | Xeon W-2255 | Xeon Silver 4314 |
| --- | --- | --- | --- |
| `new Random()` | 1,590 | 2,091 | 3,240 |
| `new Random(42)` | 1,810 | 2,470 | 3,308 |
| `Random.Shared` | 2,532 | 3,387 | 3,993 |
| криптографический | 63,589 | 72,779 | 70,485 |

Наносекунды на вызов `Next`, .NET 10. На обычном `Next` разница 1,14 раза,
криптографический генератор медленнее в 22–40 раз.

### Остальные способы

| Метод | i9-10900KF | Xeon W-2255 | Xeon Silver 4314 |
| --- | --- | --- | --- |
| `Next(0, 1000)` | 0,6318 / 2,4742 | 1,477 / 3,693 | 1,997 / 3,635 |
| `NextDouble()` | 1,9883 / 2,0042 | 1,977 / 2,444 | 3,010 / 3,637 |
| `NextInt64()` | 1,6958 / 17,4191 | 2,491 / 21,439 | 3,206 / 33,496 |
| `NextBytes()`, 1 КБ | 118,9883 / 2 078,8403 | 189,867 / 2 462,811 | 203,598 / 3 110,217 |

Наносекунды, без начального значения и с ним, .NET 10. На `NextInt64` разрыв
8,6–10,4 раза, на `NextBytes` с буфером в килобайт — 13,0–17,5 раза.
У `NextDouble` скорость одинаковая: оба алгоритма получают дробное число
одним умножением.

### Создание генератора

| Способ | i9-10900KF | Xeon W-2255 | Xeon Silver 4314 |
| --- | --- | --- | --- |
| `new Random()` | 97,56 | 118,6 | 126,8 |
| `new Random(42)` | 240,64 | 381,3 | 438,3 |

Наносекунды, .NET 10. Памяти 72 байта против 304.

### Распределение и связь соседних чисел

```
  генератор            отклонение от среднего   связь соседних

  new Random()                       0.118 %         -0.000359
  new Random(42)                     0.219 %          0.000427
  Random.Shared                      0.254 %          0.000391
```

Опечатка сказывается на длине периода, а не на равномерности. Проверка
периода требует отдельного набора тестов вроде TestU01.

## Как воспроизвести

Нужны SDK .NET 8, 9 и 10: BenchmarkDotNet поднимает по процессу на рантайм.

```
dotnet --list-sdks
```

В пути к проекту не должно быть запятых и точек с запятой. BenchmarkDotNet
собирает вспомогательный проект и передаёт путь в MSBuild без кавычек, тот
разбирает эти знаки как разделители списка свойств и падает с MSB1006.
Батник проверяет путь и останавливается сразу.

Весь прогон одной командой:

```
all.bat
```

Замеры идут тремя отдельными запусками, по классу на запуск: отчёт пишется
сразу после каждого, и обрыв в середине не съедает сделанное.

Вручную, без скрипта:

```
dotnet run -c Release -f net10.0 -- checks
dotnet run -c Release -f net10.0 -- algorithms
dotnet run -c Release -f net10.0 -- sequence
dotnet run -c Release -f net10.0 -- quality
dotnet run -c Release -f net10.0 -- --filter *NextBench*
dotnet run -c Release -f net10.0 -- --filter *MethodsBench*
dotnet run -c Release -f net10.0 -- --filter *CreateBench*
```

Аргумент `noasm` выключает снятие машинного кода.

Причина любого сбоя записывается в `Bdn\RandomProof.log`.

## Как устроен замер

Все измеряемые методы лежат в `Subjects.cs`, у каждого `NoInlining`.

Генераторы создаются в `GlobalSetup` и передаются аргументом: их создание
замеряется отдельным разделом, потому что у двух конструкторов оно устроено
по-разному. С начальным значением заполняется массив на 56 чисел, без него
запрашиваются четыре числа у операционной системы.

Отчёт `algorithms` читает поле `_impl` отражением. Имя поля задано строкой,
поэтому смена реализации сломает чтение, и сверка это заметит.

В сверке дробные числа сравниваются через `==`, и это не ошибка: проверяется
совпадение двух последовательностей, а не близость значений. Оба генератора
выполняют одни и те же операции, поэтому результаты совпадают точно.

В отчёте `quality` две проверки: распределение по десяти частям диапазона
и корреляция соседних чисел. Период они не проверяют и приведены затем, чтобы
показать: на таких проверках разницы нет.

## Что проверялось и чем

| Что проверялось | Чем |
| --- | --- |
| С начальным значением и без него работают разные реализации | отчёт `checks` читает поле `_impl` |
| Одно начальное значение даёт одну последовательность | отчёт `checks` сравнивает 1000 чисел, дробные и буфер байт |
| Без начального значения последовательности расходятся | отчёт `checks` сравнивает два генератора |
| Числа не выходят за запрошенные границы | отчёт `checks` проверяет `Next`, `NextDouble` и верхнюю границу |
| Общий генератор выдерживает несколько потоков | отчёт `checks` запускает 8 потоков по 100 000 чисел |
| Разница не в измерении, а в реализации | замеры на четырёх способах получить число |
| Дело не в конкретном методе | замеры на диапазоне, дробном, длинном и буфере |
| Дело не в сборщике мусора | режим `DOTNET_gcServer=1` |
| Дело не в конкретной машине | три машины, выгрузки всех трёх в `Results` |
| Дело не в конкретной версии | .NET 8, 9 и 10 в одном запуске |

Все замеры сняты на x64 под Windows.

По документации `Random` не рассчитан на вызовы из разных потоков. При тестах
расхождений не найдено: 8 и 32 потока по миллиону вызовов дали ту же сумму,
что и один поток. Это не повод так делать: отсутствие расхождений в одном
прогоне ничего не гарантирует.

Дизассемблер на Linux требует установленного `perf`. Выключается аргументом
`noasm`.
